Known Issues

The public application URL hangs after a successful build

If OCI Starter reports a completed deployment and the application URL does not respond, first check the public_ip_filters value and compare it with the public IP address of the machine and network used to run the build.

Why this happens: public_ip_filters controls which public IP addresses can reach an internet-facing stack. A build run from one location can complete successfully, while a browser opened from a different location is blocked by the configured network rule and appears to hang.

First check

  1. Open terraform.tfvars and find public_ip_filters.
  2. Also check $HOME/.oci_starter_profile for export TF_VAR_public_ip_filters=.... When present, this personal profile value overrides the value in terraform.tfvars.
  3. Determine the current public IP address of the network where you are opening the application URL.
  4. Compare that address with the effective CIDR list in public_ip_filters. A single IP address normally uses the /32 suffix.
public_ip_filters=["203.0.113.42/32"]

For example, if the build was run from a corporate network but the URL is opened from a home network, VPN, mobile connection, or another office, their public IP addresses may differ. The second network must also be allowed by the filter.

Repeatable diagnostic process

Run these checks from the same computer and network that is opening the application URL. First, obtain that network's current public IPv4 address:

curl -4 https://api.ipify.org

If a corporate proxy or local certificate policy prevents this command from working, use an approved “what is my IP” service in the same browser that cannot reach the application. Do not compare an IP reported by a different machine, VPN connection, or build host.

Then check where OCI Starter obtains the filter list. This prints only lines that define it:

rg -n 'public_ip_filters' terraform.tfvars "$HOME/.oci_starter_profile"

A TF_VAR_public_ip_filters export in $HOME/.oci_starter_profile overrides terraform.tfvars. Compare the browser network's public IP with the effective CIDR list.

Automation limit: A health check can verify that the service responds locally on the compute instance and that OCI has applied an ingress rule. It cannot reliably infer the browser's public IP when the browser, command line, VPN, or corporate proxy use different egress paths. The comparison must use the IP seen by the browser that experiences the problem.

Update the permitted address

Update public_ip_filters with the correct public CIDR list in terraform.tfvars, or update the overriding TF_VAR_public_ip_filters value in $HOME/.oci_starter_profile. Then preview and apply the infrastructure change.

Cloud operation: Applying the change updates OCI network rules. Limit the filter to trusted addresses; do not use a broad public range unless that exposure is intentional.
./starter.sh terraform plan
./starter.sh build

After the build completes, use the URL shown by OCI Starter or recorded in target/done.txt.

If the addresses already match

Check the build log in target/build.log, verify the application URL in target/done.txt, and confirm that the compute instance or other deployment target is running. See the User Guide for the relevant operational commands.
