OCI Starter User Guide

OCI Starter generates a working cloud-native application, its infrastructure as code, and the scripts needed to deploy it on Oracle Cloud Infrastructure (OCI). This guide explains the normal workflow first, then the operational commands you can use after deployment.

Before you begin: OCI Starter is designed for users with an OCI account and locally configured OCI credentials. Read each command before running it. Commands that create, update, stop, or delete cloud resources use your OCI credentials and may incur cost.

1. Choose a stack

At OCI Starter, choose the components for your application. OCI Starter supports several deployment targets:

Deployment targetUse it when
Public or private computeYou want a virtual machine deployment, either internet-facing or reachable only inside your network.
Instance poolYou need multiple compute instances managed as a group.
KubernetesYou need a container-orchestrated application on Oracle Kubernetes Engine.
Container instanceYou want to run a container without managing virtual machines or a cluster.
Hosted ApplicationYou want OCI to run your container images as Generative AI Hosted Applications, without managing compute instances or a Kubernetes cluster.
FunctionYou need a serverless, event-driven workload.

Select the runtime, UI, database, and deployment target, then download the generated starter.zip archive. For deployment-specific tutorials and additional architecture choices, see the OCI Starter LiveLabs workshop.

2. Generated project layout

Extract starter.zip into an empty project directory. The archive contains the project files directly under its starter/ folder.

starter/
├── starter.sh          # OCI Starter command entry point
├── terraform.tfvars    # Your project configuration
├── bin/                # Generated deployment tooling; do not edit
└── src/
    ├── app/
    │   ├── db/         # SQL scripts and database setup
    │   ├── rest/       # Backend REST application
    │   └── ui/         # Frontend application
    └── terraform/      # Terraform resources for the selected stack

3. Basic workflow

Configure required values

Open terraform.tfvars and set the values marked __TO_FILL__. For a public deployment, this normally includes:

db_password="choose-a-strong-password"
public_ip_filters=["your.public.ip.address/32"]
compartment_ocid="ocid1.compartment..."

Add every trusted CIDR to the same list when more than one network needs access:

public_ip_filters=["203.0.113.10/32", "198.51.100.20/32"]

Alternatively, keep sensitive or user-specific settings in $HOME/.oci_starter_profile as TF_VAR_* environment exports. Do not commit credentials, passwords, or private keys to source control.

Review available commands

cd starter
./starter.sh help

This command only displays the generated command reference. It does not provision resources.

Load the project environment

Run ./starter.sh env to open a Bash session configured for this OCI Starter project. It loads values in this order: deployment output in target/tf_env.sh, project values in terraform.tfvars, user overrides in $HOME/.oci_starter_profile, and optional group settings.

./starter.sh env

For an already deployed stack, the environment includes project and Terraform variables plus deployment details such as the compute connection settings and database connection information. For Kubernetes stacks, it also sets KUBECONFIG. Type exit to leave the shell. To load the same settings into your current Bash session, run:

source ./starter.sh env

The command checks required local tools and may query OCI to populate deployment details, but it does not create or change OCI resources.

Worked example: Python, ReactJS, and Autonomous Database on public compute

The generated public-compute sample contains a FastAPI REST service, a ReactJS frontend, and an Autonomous Database schema. The REST service exposes /dept for department data and /info for a stack description. The React frontend lives in src/app/ui; the SQL schema is in src/app/db.

Cloud operation: ./starter.sh build connects to OCI, applies Terraform, creates the stack’s configured resources, configures the database, and builds/deploys the backend and UI. Review the Terraform plan and cost implications first.
./starter.sh terraform plan
./starter.sh build

After deployment, OCI Starter displays the deployed application URL. For a public-compute deployment, it is typically http://compute-ip. You can view the URL again at any time in target/done.txt.

Inspect logs

cat target/build.log
cat target/destroy.log

OCI Starter retains timestamped logs under target/logs/. Use them first when a build or destroy operation does not complete as expected.

4. Advanced and operational actions

Use a personal OCI Starter profile

$HOME/.oci_starter_profile is an optional, user-local shell file for settings you want to reuse across OCI Starter projects or keep outside the project directory. OCI Starter reads it after terraform.tfvars, so its TF_VAR_* exports take precedence over the same project values.

# $HOME/.oci_starter_profile
export TF_VAR_compartment_ocid="ocid1.compartment..."
export TF_VAR_region="eu-frankfurt-1"
export TF_VAR_public_ip_filters='["203.0.113.42/32"]'

Add every trusted CIDR to the same JSON list in the profile.

This is useful for personal defaults such as a compartment, region, or the public IP range from which you normally build and access stacks. Project-specific values can remain in terraform.tfvars.

Protect this file: It can contain sensitive settings. Keep it in your home directory, restrict its file permissions, and never commit it to source control. Do not add private keys, passwords, or values that you would not want exposed in a terminal log.

To confirm the effective configuration for a project, open the OCI Starter environment:

./starter.sh env

OCI Starter loads values in this order: deployment output in target/tf_env.sh, terraform.tfvars, then $HOME/.oci_starter_profile. The later profile values override earlier values with the same TF_VAR_* name.

Redeploy application changes

After changing files under src/app/, including the FastAPI backend or ReactJS frontend, redeploy the application portion:

Cloud operation: This command connects to OCI and updates the deployed application. It does not perform the full Terraform and database build.
./starter.sh build app

Preview infrastructure changes

Use a Terraform plan before changing infrastructure configuration or Terraform files:

./starter.sh terraform plan

A plan reads the current OCI state and uses your configured OCI credentials, but does not apply the proposed changes.

Connect to deployed resources

For a compute deployment, open an SSH session after the stack has been built:

./starter.sh ssh compute

Other generated targets can expose ssh bastion or ssh db_node. Use ./starter.sh help to see what your stack supports.

Manage a stale build lock

If a previous build stopped unexpectedly and reports that another build is active, clear only the stale lock:

./starter.sh unlock

Start and stop supported resources

Cloud operation: These commands use the OCI CLI to start or stop supported resources recorded in the Terraform state.
./starter.sh start
./starter.sh stop

Destroy the stack

Destructive cloud operation: ./starter.sh destroy removes Terraform-managed OCI resources associated with this project and resource prefix. Review terraform.tfvars, the Terraform plan, and the generated logs before running it.
./starter.sh destroy

5. Customize safely

  • Change backend logic in src/app/rest.
  • Change the ReactJS application in src/app/ui/src.
  • Change database objects in src/app/db.
  • Review infrastructure changes in src/terraform with ./starter.sh terraform plan before applying them.
  • Do not modify generated files in bin/; use application and documented configuration extension points instead.

For a guided, deployment-specific walkthrough—including more architecture and customization options—continue with the OCI Starter LiveLabs workshop.
